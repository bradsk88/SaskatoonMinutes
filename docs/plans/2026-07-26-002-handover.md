## What happened

### 1. The index cards now use the ItemSummary — done

`_format_topic` in `app/summarizer.py` used to show the first 120
characters of the raw eSCRIBE blob. It now:

- Prefers `item["summary"]["description"]` and shows it **whole**. The
  Description is already bounded at 220 characters and written as a lede;
  re-truncating it is what it existed to stop.
- Falls back to the old 120-character clip for a Legacy summary, and
  **marks it** — new key `summary_is_description`, rendered as
  `.topic-summary-raw` (italic, dimmed, tooltip). Never silently mixed.
- Adds chip badges: `Cost & Funding` plus `SEMANTIC_CATEGORIES`, capped at
  3, deduped by category. Label is the category, tooltip is the chip
  sentence. Coloured with the detail page's existing `chip-<group>`
  classes so a category looks the same in both places.
- Drops regex money badges to one when chips are present.
- Ranks with `+0.15` per chip badge, capped at `0.4`.

Verified against a real build: card summary is byte-identical to the
detail page description, card chips are the first three interpretive
chips, `Outcome`/`Vote Breakdown` correctly excluded. Across the built
index: 2,162 topics, 370 with a description, 406 with chip badges, 1,792
on the marked raw fallback.

### 2. `[object Object]` on the detail page — fixed

Two producers wrote different types to `item.summary`:
`summarize_agenda_items` wrote a string, `build_site.py` wrote the
ItemSummary dict. `meeting.html` interpolated it into a template literal.

Fixed by splitting the keys, not by a type check: `summary` is the
ItemSummary object (its canonical owner — the template already read
`summary.description`/`.chips` elsewhere), and the extractive one-liner
moved to `extractive_summary`. Also added the missing `escapeHtml` on
that line. Zero occurrences of "object Object" in the built site.

### 3. The summarize run — the real finding

It landed at 07:54 UTC. 102 meetings now have current-format files, up
from 1. **35 of them have every description null.**

Those 35 produced only `Outcome`, `Vote Breakdown` and `Cost & Funding`
chips — and **zero** categories from `SEMANTIC_CATEGORIES`. Those are the
LLM-only ones, so Gemini did nothing for those meetings.

Commit order shows the shape:

```
05:26  ........................................   . = descriptions present
05:47  .............X..............XXXXXXXXXXXX   X = degraded
07:54  XXXXXXXXXXXXXXXXXXXXXX
```

53 meetings clean, then failing from 05:53 onward and never recovering.
That is quota exhaustion, not a transient.

**Why it kept going — four layers, none treats it as an error:**

- `app/item_categorizer.py:575` — `GeminiExtractor.extract` has a bare
  `except Exception`, prints one line, returns `(None, [])`. Quota, 429,
  auth and network all land here. Nothing counted, nothing re-raised.
- `scripts/summarize_meetings.py:127` — `summarize_meeting` counts
  `missing_description`, prints a per-meeting WARNING, and returns the
  degraded summaries anyway.
- `scripts/summarize_meetings.py:237` — `main` saves that and does
  `summarized += 1`. A meeting with zero descriptions counts as a
  **success**. `errors` only increments on an exception escaping
  `summarize_meeting`, which the per-item catch guarantees never happens.
- Exit code — `sys.exit(1)` only when `errors > 0`, so the run **exited
  0** having written 35 empty meetings. `GitBranchCache` pushes on
  `__exit__` regardless.

**No retry or backoff anywhere.** No `sleep`, no 429 handling, no
`RESOURCE_EXHAUSTED` check in either file. First rejection is final, and
the loop immediately tries the next item at 8 workers.

`is_current()` returns False for all 35, so the next run redoes them —
nothing is permanently lost, but the run burned a third of its work and
reported success.

**Why 102 meetings when the dispatch said limit 5:** `--limit` is per
tab, so the ceiling was 5 × 16 = 80. `summarize.yml` also triggers on
`workflow_run` after Transcribe, and `concurrency.cancel-in-progress` is
`false`, so a second run **queues rather than cancels**. The 07:54 batch
of 28 is 100% degraded — consistent with a second run starting after the
quota was already gone. Not proven without the Actions log.

## Traps

- **`build_site.py` writes `_site/`, not `dist/`.** The previous handover
  said `dist/`; that cost a minute.
- **It hits eSCRIBE for every meeting and takes a long time.** Run it in
  the background and monitor the log. It emitted zero warnings this time,
  so a clean run is achievable — do not put it in an edit loop.
- **The index page is built twice** (`build_site.py` static,
  `app/main.py` live) and the card markup is **JavaScript inside
  `index.html`**. Editing Python alone changes nothing a user sees.
- **`app/main.py` never attaches ItemSummary** — not on
  `/api/meeting/<id>/topics` and not on the detail endpoint. The live dev
  server has never shown descriptions or chips on any page; only the
  static build does. Wiring it in means opening `ItemSummariesCache` per
  request, which fetches from origin and creates a git worktree. Not
  viable in a request. Pre-existing gap, deliberately left alone.
- **Commit timestamps on `summaries` are when the work happened, not when
  it became visible.** The cache commits locally per meeting and pushes
  once at `__exit__`. A fetch mid-run shows nothing and that is not a
  failure. This is why the run looked absent at 05:46 and complete at
  07:54.
- **To tell a degraded run from a healthy one offline**, check which chip
  categories came back. Zero `SEMANTIC_CATEGORIES` means the LLM never
  answered, whatever the file count says.

## Settled in the grill — and implemented

1. **"Loud" is the exit code.** Not refusing to write: `is_current()`
   already rejects a degraded meeting, so a written one self-corrects on
   the next run, and the cache pushes on `__exit__` regardless.
   - **Action for Brad, not code:** GitHub emails on a failed run only if
     the account setting is on. Settings → Notifications → Actions →
     "failed workflows only", Email ticked. Nothing in the repo can turn
     this on.
2. **Retry a rate limit, never a spent quota.** Gemini names the quota in
   a 429, so the two are told apart: `...PerDay...` stops the run on the
   first rejection; `...PerMinute...` waits the server's own `retryDelay`
   (capped at 60s) for up to 3 attempts. An unrecognised 429 gets two
   attempts, then is treated as quota. Retrying a day quota is pointless
   — the run is unattended and the next one redoes the meetings free.
   - `EXTRACT_WORKERS` dropped 8 → 4. Eight workers could trip the
     per-minute cap on their own; not creating the limit beats waiting
     it out.
3. **Partial meetings split by cause, not by count.** A count threshold
   would need `is_current()` tightened, and then a meeting where the
   model legitimately declined one item is redone forever — the run
   stops converging.
   - Call failed → `ExtractionFailed`, the meeting is **not saved**, the
     next run redoes it.
   - Model answered and declined → real outcome, saved, current.
   - Nothing about the cause is persisted or user-facing. The card's
     existing marked raw fallback is unchanged.
4. **`cancel-in-progress` stays `false`.** The quota abort already fixes
   the queued-run problem: it now exits in seconds instead of grinding
   through 28 meetings. Cancelling would kill a 350-minute job mid-flight
   and cancel the legitimate post-Transcribe run.

### Known trade-off, accepted

A response that arrives but does not parse is treated as a failure, not a
decline. If one item were to fail that way every time — a truncated
response on a very long item is the plausible case — its meeting would
never save. That is loud and diagnosable rather than silent, which is the
side to err on, but it has not been seen in practice and is worth
remembering if a single meeting starts failing repeatedly.
