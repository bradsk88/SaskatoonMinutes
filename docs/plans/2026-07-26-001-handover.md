## The task

The detail page now shows a mandatory plain-language **Description** plus
**Chips** per agenda item (ADR `0003`). The **meeting index cards do not
use any of it.** Make the cards benefit from that work.

### Where the cards come from

- `scripts/build_site.py` → `fetch_meeting_topics` builds `topics_data`,
  which is preloaded into the page as `#preloaded-topics`.
- The card HTML is built **in JavaScript**, not server-side:
  `buildCardHTML` and `renderTopicsTable` in `app/templates/index.html`.
- Each topic row comes from `_format_topic` in `app/summarizer.py`.

### The finding worth starting from

`scripts/build_site.py` attaches each item's ItemSummary *before* it calls
`extract_meeting_topics` on the same list — so `item["summary"]` is
already there when `_format_topic` runs. It ignores it:

```python
content = item.get("content", "")
summary = ""
if content:
    summary = clean_entities(content)
    if len(summary) > 120:
        summary = summary[:117].rsplit(" ", 1)[0] + "..."
```

That is the raw eSCRIBE agenda blob, truncated mid-sentence at 120
characters — the exact thing the Description was introduced to replace on
the detail page. The data to fix it is already in the dict.

## Do this next

1. **Use the Description in `_format_topic`.** Prefer
   `item["summary"]["description"]`, fall back to the truncated content
   only for a Legacy summary. Descriptions are bounded at 220 characters
   and written as a lede, so decide a card-length policy rather than
   re-truncating blindly.
2. **Consider chips as card badges.** `_extract_badges` currently derives
   its own money/person/location badges from raw text. Real chips —
   `Dissenting View`, `Public Sentiment`, `Cost & Funding` — are better
   evidence of "this item is worth opening" than a regex over the title.
3. **Consider ranking by chips.** `extract_meeting_topics` scores on
   contested votes, dollar signs and section depth. An item that produced
   soft chips is, by construction, one the model found something to say
   about.
4. **Exit check:** `./venv/bin/python scripts/build_site.py` (needs
   network and the cache branches), then open `dist/index.html` and
   compare a card against that meeting's detail page.

## Traps

- **The index page is built twice.** `scripts/build_site.py` hand-flattens
  the Jinja blocks into static HTML for GitHub Pages, and `app/main.py`
  serves the same data live. A change that only works in one path will
  look fine locally and ship broken.
- **Card markup is in JavaScript inside `index.html`.** Editing the
  Python alone changes nothing a user sees.
- **Legacy summaries are the common case right now** and will be for
  days. A card that assumes a description exists will render empty for
  most meetings. The detail page's handling (`is_legacy`, marked as
  lower-confidence) is the pattern to follow — do not silently fall back
  in a way that hides which is which.
- **Outcome labels changed yesterday.** A public hearing's recorded vote
  is first reading, not approval, so cards will now show "First reading
  passed" where they used to say "Approved" — that is correct, not a
  regression. See ADR `0005` and the plan's U10.
- **`build_site.py` hits eSCRIBE** for every meeting on every run. It is
  slow and rate-limitable; do not put it in a tight edit loop.
